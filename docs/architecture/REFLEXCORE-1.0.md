# ReflexCore 1.0 · Architecture Blueprint

**Статус — предложение.** Цель версии 1.0 — провести пользовательскую задачу от намерения до независимо проверенного результата, пережить потерю воркера и использовать подтверждённый опыт в следующем запуске. Первая реализация остаётся в существующем Rust crate, с одним исполняемым файлом, управляемыми воркерами и нынешней файловой очередью Windows.

| Planning | Дейкстра из Goal Agent | Проверенные начальные факты, цель, доступные навыки и стоимости → упорядоченные версии навыков | Детерминированный выбор. При изменении среды Runtime может запросить новый план |
| World Model | Новый модуль поверх observer, UIA и чтения принадлежащих задаче артефактов | Область наблюдения → датированные факты | Свежесть, идентичность объекта, различение несовпадения и недоступности источника |
| Execution Runtime | Goal Runtime, Flow, реестр, существующий UIA worker | План и полномочия задачи → квитанция выдачи действия | Владение задачей, последовательность, отмена, дедлайн и выбор адаптера. Очередь сохраняет единоличное владение интерактивной полосой исполнения |
| Verification | Новый модуль поверх существующего UIA readback и независимой проверки файла | Контракт эффекта, квитанция и свежие наблюдения → заключение | Только зарегистрированный верификатор может подтвердить эффект. Runtime проверяет полноту цели |
| Memory & Learning | Существующая SQLite и экспериментальный локальный Neural Runtime | Завершённая попытка, заключения и контекст → статистика и предложения стоимости | Идемпотентное обновление опыта. Планировщик получает ограниченную поправку. Обучение весов выполняется отдельно |

Сначала выделяются Rust-модули типов, состояния, верификации и жизненного цикла. Windows-адаптер владеет COM-вызовами и дескрипторами. Studio, CLI и трей остаются клиентами существующих протоколов. Старые команды демонстрационного автомата можно направить в модуль `legacy_demo` через совместимые алиасы. Вынос в Cargo workspace оправдан, когда у модуля появятся стабильный контракт и второй независимый потребитель.

## Task, запуск и эффект

Идентификатор записи очереди остаётся `task_id`. Для прямого CLI Runtime создаёт ID задачи на входе. `run_id` обозначает конкретную попытку. `plan_revision` меняется при перепланировании. `effect_id` обозначает одно намерение изменить объект, а `action_id` связывает конкретный запрос и ответ воркера. Типы-обёртки сохраняют существующие строковые ID на границе с Studio и PowerShell.

| Переход | Условие и действие Runtime |
| --- | --- |
| Created → Planning → Ready | Валидация цели, схемы, разрешений, совместимости навыков и стоимости. Зафиксировать версии навыков и план |
| Ready → Executing | Получить свежие предусловия. Проверить владение целью, отмену и дедлайн. Записать намерение перед выдачей изменяющего действия |
| Executing → Verifying | Сохранить сведения о выдаче. Верификатор проверяет обязательные эффекты в пределах срока, допустимого для приложения |
| Verifying → Ready / Completed | Продолжить со свежего состояния или отдельно проверить конечный предикат цели. Для пустого маршрута также требуется проверка цели |
| Blocked / Recovery | При утрате предусловия прекратить текущий маршрут. После нового наблюдения разрешено ограниченное перепланирование. Повтор того же плана при тех же фактах заканчивается Blocked |
| Stopping → Cancelled | Закрыть выдачу новых действий, дождаться очистки или зарегистрировать таймаут. При живом неподтверждённом воркере полоса остаётся занятой. Поздний ответ не возобновляет задачу |
| Failed / Unknown | Failed означает установленное невыполнение контракта. Unknown сохраняет неопределённость эффекта. Для восстановления допускается повторное чтение результата |

Фаза задачи и состояние эффекта хранятся отдельно. Например, оператор может отменить задачу после Save. Итогом будет Cancelled с неизвестным эффектом. Если подтверждено только одно из двух обязательных изменений, интерфейс показывает частичный результат и перечисляет статусы обоих эффектов. Обычный скрипт с успешным кодом выхода сохраняет подпись *Finished without verification*.

### Журнал и восстановление

Файловая очередь сохраняет полномочия на запуск. Приватный журнал в существующей SQLite хранит события и проекцию состояния попытки. Единственный владелец попытки пишет событие и обновляет снимок в одной транзакции с проверкой предыдущей версии. Уникальный ключ события — `(task_id, run_id, sequence)`. Для изменения обязательна долговечная запись `DispatchIntent` до отправки команды. Сбой записи останавливает выдачу.

После перезапуска очередь изолирует оставшуюся активную запись. Сначала выясняется, завершён ли принадлежащий задаче воркер. Намерение без окончательного доказательства считается потенциально исполненным, даже если отсутствует запись об ответе. Восстановление получает новый запуск, ссылающийся на предыдущий эффект, и начинает с чтения. Подтверждённый терминальный результат публикуется в очередь атомарно. Если процесс упал между фиксацией в SQLite и публикацией, повторяется только публикация той же квитанции. При конфликте с уже записанным исходом сохраняется ошибка согласования и прекращается автоматическая обработка. Журнал и файловая система имеют разные границы транзакций.

## Контракты наблюдения, навыка и доказательства

Эскиз типов для первого среза. Ссылки на объекты действуют только в пределах разрешённой области задачи.

```rust
enum Predicate {
    ControlValueEquals { target: TargetRef, expected: InputRef },
    OwnedFileContentEquals { artifact: ArtifactRef, expected: InputRef },
}

enum Finding {
    Confirmed(EvidenceId),
    Mismatch(EvidenceId),
    Unknown(ReasonCode),
}

trait Observer {
    fn observe(&self, scope: &ObservationScope, budget: &Budget)
        -> Result<Observation, ObservationError>;
}

trait Verifier {
    fn check(&self, claim: &EffectClaim, observation: &Observation) -> Finding;
}
```

**Observation** содержит источник, область, поколение цели, последовательность и момент наблюдения. UTC нужен для истории, монотонное время — для локальных дедлайнов. После перезапуска кэш наблюдений сбрасывается. Для действия по UIA проверяются принадлежность окна, идентичность элемента и применимые требования фокуса непосредственно перед выдачей. Совпавший индекс пути ускоряет поиск. При неоднозначности окна или смене элемента требуется новое разрешение цели.

**SkillDescriptor** содержит ID, версию, категорию, типы входов, требования к среде, предусловия, обязательные эффекты, ID верификатора и режим повтора. Реестр связывает дескриптор с реализацией Flow или встроенным адаптером. Контракт предикатов использует закрытый набор операций. Доверенный верификатор выбирается каталогом. Навык возвращает квитанцию выдачи и диагностический код. Для пакетного результата верификатор явно перечисляет покрываемые эффекты. [Реестр лабораторных навыков](https://github.com/triple6xseven/ReflexCore/blob/8d8f227/src/skill_registry.rs#L22)

**Evidence** связывает задачу, запуск, эффект, объект, предикат, наблюдение, источник и версию верификатора. До принятия результата Runtime сверяет эту связь, свежесть и допустимость источника. Положительный факт до выдачи может подтвердить уже достигнутую цель. В статистику выполненного действия такой факт не засчитывается. При временной задержке приложения отрицательное наблюдение допускает повторное чтение до дедлайна. Истечение срока само по себе даёт Unknown, если у верификатора отсутствует достаточное доказательство отказа.

### Один сквозной сценарий — Save

1. Пользователь разрешает сохранить тестовый документ. Адаптер закрепляет редактор, ожидаемый контент и конкретный выходной артефакт. Первое наблюдение устанавливает исходное состояние. Для контракта именно *создания* требуется предварительно установить отсутствие файла либо получить право на эксклюзивное создание.
2. Первый навык записывает текст. UIA readback подтверждает значение того же редактора. Второй навык повторно проверяет предусловия. Подмена окна между навыками переводит задачу в Blocked до отправки Save.
3. Runtime фиксирует намерение Save. Допустим, воркер завершился после выдачи команды. У эффекта теперь статус Unknown. Адаптер независимо читает закреплённый выходной файл и сверяет содержимое. При подтверждённой принадлежности и совпадении обязательных условий цель может завершиться.
4. После перезапуска ожидаемый результат может быть восстановлен из версии известного тестового сценария или из разрешённого приватного источника. Если потеряна идентичность артефакта или ожидаемое значение, остаётся Unknown. Самопроизвольный повтор Save запрещён. Новое действие требует подтверждённого исходного состояния и разрешённого контрактом повтора.

## Память, приватность и участие LLM

- **Semantic** — версионированные описания навыков и совместимых адаптеров. **Episodic** — ограниченная история отдельных попыток. **Procedural** — проверенные варианты выполнения и их применимость. Существующие каталог и SQLite обслуживают эти роли. Полные записи активных и незакрытых эффектов сохраняются до завершения восстановления, затем применяется ограничение хранения.
- Для надёжности использовать `skill_id + skill_version + implementation_hash + verifier_version + environment_compatibility`. Стоимость ребра и позиция в манифесте исключаются из идентичности. Старую статистику переносить лишь при однозначном соответствии старого Goal, слота и отпечатка. Готовить миграцию в транзакции, сохраняя старые строки на период отката.
- В пределах одного контекста считать подтверждённые успехи и отказы, отдельно — Unknown, отмены, восстановления, задержку и свежесть. При публикации повторной квитанции уникальный ключ попытки навыка предотвращает двойной учёт. Новая версия верификатора или несовместимое обновление приложения начинает отдельную выборку. Высокая доля Unknown служит показателем качества наблюдения.
- В события и экспорт попадают разрешённые коды, ID, версии, длительности и счётчики. Текст, имена окон, пути, снимки и хеши пользовательского содержимого исключаются из общих квитанций. Память опыта и диагностический экспорт используют отдельные сериализуемые типы.
- Ollama предлагает дерево подзадач с ID известных навыков и ссылками на типизированные входы. Валидатор ограничивает глубину, число узлов и бюджет, проверяет циклы и область разрешений. Неизвестная операция отклоняется до планирования. Предложенный новый навык проходит проверку схемы, испытания на изолированном стенде и явное включение в доверенный каталог. При недоступности модели для структурированной цели остаётся детерминированный маршрут.

Невыполнимый план и недоступный адаптер завершаются до мутации. Замеряются качество, время и память при включённой и отключённой модели |

Для каждого PR фиксировать коммит, среду, размер выборки, долю Verified/Failed/Unknown, p50/p95 и пик памяти. Синтетический воркер проверяет протокол и аварийные окна. Один короткий оконный сценарий проверяет реальный адаптер при разрешённом вводе. Первый показатель для 1.0 — число ложных Verified в тестах с потерей доказательств, подменой окна и аварийным завершением. Целевое значение — ноль.
